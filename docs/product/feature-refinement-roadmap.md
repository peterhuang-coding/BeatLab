# BeatLab 功能精炼路线图（score song 审阅方向）

本路线图只覆盖本地 score song 的试听反馈与来源透明化，按顺序排列、每项范围有界。
所有条目遵循同一前提：

- **父版本不可变**：反馈只生成新版本目录，旧版本（含 `full_mix.wav`、`score.json`、
  `run_manifest.json`）永不覆盖、不自动删除（现有 `pipeline/song.py` 已强制空目录渲染）。
- **听感验收在人**：工具只呈现信息与候选，不打分、不推断偏好；"用户会喜欢"没有自动化
  结论，所有版本在真人试听前一律标注待试听。
- **记录反馈 ≠ 自动实现反馈**：页面上记录的时间点意见、层意见是给人看的信息，不会
  自动触发改词、换采样或重新编曲；是否落地由人在后续有界任务中决定。
- **商业使用暂缓**：`run_manifest.license` 只作为已记录的制作/授权信息呈现，不授予
  作曲或采样权利，也不等于任何采样或历史录音的商用授权；`needs_review` /
  `unavailable` 状态未人工销项前，不安排任何商业发布。
- **不恢复已过期的算法冲刺**：不重新发起来源与状态不明的远程请求；淡出、时间拉伸、
  节拍网格基准、音频客观指标等方向不在本路线图内，除非未来另行明确立项。

状态图例：待集成 = 代码已完成，等待父任务接入；待验收 = 并行任务已有产出但尚未被
父任务接受，不得视为已完成；待启动 = 仅有计划。

## F01 时间戳听感批注（技术通过，待用户验收）

> 注意：F01 由独立并行任务实现，其结果在通过父任务评审、确认与下列契约一致之前，
> 不得标记为已完成；本文不为该并行任务引用任何测试数字。

- **用户价值**：试听时能指着"第 32 小节进副歌那一下太抢"这类具体时间点记录意见，
  沟通成本从"感觉不对"变成可定位的条目，便于之后逐项决定是否改动。
- **当前缺口**：`pipeline/song_review.py` 目前只有整轨音量选择（−3/−6/−60 dB），
  没有任何时间点注释；关掉页面意见即丢失。
- **契约（具体验收）**：
  1. 审阅页可在 `full_mix.wav` 时间轴上按当前播放位置新增批注，字段为
     `timestamp` / `category` / `text`；时间戳一律使用 UTC；`text` 有长度上限
     （bounded），超长请求被拒绝；不修改音频与既有清单；
  2. 批注只通过 `POST /api/listening-notes` 写入仓库根（`ROOT`）下的 append-only
     SQLite 数据库 `listening-notes.sqlite`；**不向任何 song 版本目录写文件，
     不在不可变 song 文件夹内写 JSON**；`GET /api/listening-notes` 负责读取，
     刷新页面后批注仍在；
  3. 每条批注以 `run_id` 与实际 `full_mix` 的 SHA256 定位；提交的 mix SHA256 与
     当前实际 mix 不一致时返回 `409`（stale），拒绝把意见挂到错误版本；
  4. `POST` 必须带客户端生成的 `request_id`；同一 `request_id` 重试不重复落库
     （幂等）；
  5. 批注是独立信息，不自动生成新版本、不改任何层增益；存储不可写时只提示失败，
     不影响试听与现有反馈按钮；
  6. 合成夹具测试（TemporaryDirectory 内的临时 sqlite）覆盖新增 / 读取持久化 /
     `request_id` 重试幂等 / stale `409` / 存储失败路径；不使用真实媒体库，
     不启动生产服务器、不访问外部网络。
- **依赖**：父任务在 `song_review.build_page` 中接入 F01 区块与上述 API，前置条件
  是并行交付物通过父任务评审且与本契约一致；真人试听验收；不依赖任何外部网络服务。

## F02 素材来源与授权记录呈现（技术通过，待用户验收）

- **用户价值**：每轨用了什么采样、记录的来源、URL 与商用状态一目了然，在做任何分享
  或商业决定前就能看到缺口，而不是事后追溯。
- **当前缺口**：demo 已在歌曲目录生成 `source-provenance.json`
  （见 `examples/borrowed_light_demos.py`），但审阅页完全不展示；真实清单中多数
  素材仍是 `needs_review`。
- **交付物**：`pipeline/song_provenance.py` 中的
  `render_source_section(song: Path, manifest: dict) -> str`，配套
  `tests/test_song_provenance.py`（30 个用例，以授权 unittest 命令实跑为准）。
- **具体验收（集成后）**：
  1. 父任务把该函数输出嵌入 `song_review.build_page`，真实 demo 页面出现可折叠中文
     来源区块，摘要行显示"已用 N 轨 · 已匹配 M · 存疑 · 缺失"；
  2. 区块只读取 song 目录下的普通文件 `source-provenance.json`，不跟随符号链接，
     不读取任何采样音频、不联网、不写文件、无新依赖；
  3. SHA256 一律标注"记录值，未重新校验"；匹配仅限精确 ID 与精确哈希：ID/哈希分别
     命中不同记录、同一 ID 或哈希多重命中、或 ID 一致但双方非空哈希冲突时，一律存疑
     且不采用任何来源/授权信息（摘要计入"存疑"，不计"已匹配"）；音轨缺少哈希时只是
     未核验的 ID 匹配，不称为哈希冲突；未被任何 ID/哈希引用的清单记录不出现，存疑
     候选记录在页脚标注"未建立唯一对应"，不得仅因匹配失败就称其"未被使用"；
  4. 页面不出现本机绝对路径（仅文件名）；`javascript:`/`data:`/带凭据 URL 不成为链接；
     run_manifest 的制作/授权记录与单轨授权状态分区显示，并声明前者仅为记录值、
     不授予作曲或采样权利；清单记录提供安全 http(s) `source_url` 时，作为"素材来源
     URL"单独成行显示（不访问网络、不读取源音频），与 `license_source` 分开；
  5. 清单缺失、JSON 损坏、顶层为字典、坏行等情况只产生中文警告，页面其余部分正常。
- **依赖**：父任务集成（本任务不修改 `song_review.py`）；集成后需在真实
  borrowed-light demo 目录人工核对一次显示内容。

## F03 版本对比（保留不可变父版本，状态：今晚执行，依赖F01/F02推送）

- **用户价值**：反馈版与父版并排可比，人可以确认"改的是不是我说的那一处"，避免
  版本越改越多却分不清差异。
- **当前缺口**：现有流程可生成反馈版（固定父增益、只改指定层 dB），但没有只读的
  版本对比视图；"父版本不可变"规则分散在各脚本中，没有在页面上明示。
- **具体验收**：
  1. 提供只读对比页/区块：两版标题、BPM、小节数、时长、母带增益、各层增益与
     SHA256 并列；父版本目录在整个流程中不被写入（测试用临时目录验证）；
  2. 对比不重新渲染、不复制音频，只读取两个版本的 manifest；差异用文字描述
     （例如"snare −6 dB"），不输出"哪个更好"的结论；
  3. 不提供删除/覆盖旧版按钮；版本谱系（parent_run、parent_mix_sha256）缺失时
     明确标注"无法确认父版本"，而不是猜测。
- **依赖**：F01 提供对照时参考的听感意见；现有 `/api/revise` 与
  `pipeline/song.py` 的固定父增益策略；F02 区块在两个版本页面中均可独立显示。

## F04 人工可编辑的来源乐句选择（状态：待启动）

- **用户价值**：人可以从本地候选乐句里挑用哪一句、换哪一句，采样取舍保持显式、
  可追溯，而不是由"自动 Hero Sample 选择器"替人决定。
- **当前缺口**：borrowed-light demo 的 phrase chop（`phrase_<chord>_<part>`）由
  `examples/borrowed_light_demos.py` 脚本固定；想换乐句必须改脚本并重跑，且这些
  轨道目前在来源清单中没有对应记录（F02 会如实显示为缺失）。
- **具体验收**：
  1. 审阅页列出某版本可用的本地候选乐句（仅文件名 + 来源记录行，不含绝对路径），
     人勾选/替换后生成**新的版本草稿**，父版本不动；
  2. 每次人工选择写入新版本 manifest/provenance（选了哪条候选、对应原始乐句与
     记录哈希）；无来源记录的候选必须标红提示，不能静默使用；
  3. 不自动发布、不生成品味评分；候选的生成仍走现有受控脚本，不引入网络选样；
  4. 全部测试使用 TemporaryDirectory 合成夹具。
- **依赖**：F02（先让来源/授权状态可见、缺失可见）；F03（新旧版本对比确认变化）；
  真人试听验收；商用授权状态未销项前候选仅用于私下创作。

## F05 编排 / pattern 迭代（状态：待启动）

- **用户价值**：在不推翻父版本的前提下，有界地尝试段落开关、节奏型替换等编排变化，
  每次变化可比较、可回退。
- **当前缺口**：pattern（bass 进行、鼓点、人声呼应等）写死在示例脚本里；一次编排
  调整等于改脚本重渲染，且改动内容没有统一的可读 changelog。
- **具体验收**：
  1. 提供参数化的有界编辑（例如指定小节段静音/恢复、在已有人工编写的 pattern 预设间
     替换），输出新版本目录并在 manifest 记录逐条 changelog；
  2. 不修改父版本任何文件；不引入自动配器"优化"、不根据听感指标自动决策；
  3. 新版本页面保留"待试听"状态，F01 的意见与 F03 的对比可直接使用；
  4. 明确不恢复已过期算法冲刺中的淡出、时间拉伸、节拍网格基准与音频客观指标工作，
     也不因其旧远程请求状态不明而重试。
- **依赖**：F03 的版本谱系与对比；F01 的人工意见作为输入之一（仅输入，不自动执行）；
  真人对每个新版本做听感验收。

## F06 Ableton Live 实际打开 / 播放 / 重渲染核对清单（状态：待启动）

- **用户价值**：确认导出的 Live 工程在真实 Ableton Live 12 里能打开、逐轨发声、
  重渲染音频与本地交付 WAV 听感一致（等价标准见下，非比特一致）——这是"导出成功"
  和"音乐真的对"之间最后一道人工关。
- **当前缺口**：`validate_song` 只做脚本侧校验；Live GUI 内的实际打开、播放、
  采样丢失检查与重渲染对比一直挂起为人工事项，审阅页也只写了"Ableton 实际发声与
  听感另行验收"。
- **具体验收**：
  1. 在 `docs/` 下落一份人工 checklist：Live 版本、打开工程无离线采样、逐轨独奏播放、
     全曲播放、Rack（Phrase Pads）打击垫触发检查；重渲染核对必须区分两类判断——
     文件 SHA256 只用于标识文件身份（是否同一个文件），Live 用相同工程重新导出的 WAV
     **不要求与交付 WAV 比特一致**（容器元数据/导出舍入差异不代表音频不同）；音频
     等价性以时长对齐、波形/残差对比（记录对齐方法与容差）或文档化容差下的人工试听
     为准；
  2. 每次核对结果写入 evidence（日期、版本 run_id、检查人、发现项），未完成的版本在
     审阅页持续显示"Live 内待验收"，不允许勾选成已完成；
  3. 清单只记录事实，不把"工程打开成功"表述成"音乐好听"或"可以商用"；
  4. 不安装新依赖、不启动任何网络服务；该任务以人工操作为主，不做自动化 GUI 脚本。
- **依赖**：本机 Ableton Live 12 Suite 授权环境；F03/F04 产出的待核版本；
  F02 的来源区块用于在核对时同时确认采样授权状态。

## 完成顺序建议

F02 区块已在本任务内实现并通过合成夹具 unittest，等待父任务集成进
`song_review.build_page`（父任务应用更改后才是最终接受）。F01 为独立并行任务：
其交付物在通过父任务评审、确认符合上述契约之前，**不得视为已完成**，本文也不引用
其测试数字。F03 / F04 / F05 目前都只是计划（待启动），尚无任何实现；集成确认后再做
F03（比较能力是后续一切迭代的安全网），随后 F04、F05 交替推进，每个新版本都经过
F01 收集意见、F03 对比、F06 人工 Live 验收。任何一步发现授权状态不清，记录在 F02
区块中并暂停对外使用，而不是补一个自动判断。
